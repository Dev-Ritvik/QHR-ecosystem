## [2026-07-15 22:11 IST] Issue: notify_lead_assigned ON CONFLICT cannot match partial dedupe index
- Found: `packages/db/migrations/0011_notifications.sql:36` — trigger function used bare `ON CONFLICT (dedupe_key) DO NOTHING`, but `notifications_dedupe_uq` is a **partial** unique index (`WHERE dedupe_key IS NOT NULL`). Postgres cannot infer a partial index from a bare conflict target, so the INSERT inside the trigger fails at plan time with error 42P10 — which aborts every lead INSERT with an assigned agent and every reassignment UPDATE.
- Why it matters: lead creation/assignment would hard-fail whenever the trigger fires — core CRM flow broken, not just missing notifications.
- Fix applied: LIVE database function `core.notify_lead_assigned()` already contains the corrected form `ON CONFLICT (dedupe_key) WHERE dedupe_key IS NOT NULL DO NOTHING` (patch from prior session was applied live). This session synced the drifted migration file: edited `0011_notifications.sql:36` to the same corrected form so fresh deploys don't reintroduce the bug. No new migration number needed — live already correct; no app-level migration tracking table exists (only Supabase-internal auth/realtime/storage schemas), so editing the file breaks no checksums.
- Verified (all against LIVE db `dhmatgzlqoogsnerdfsl` via the repo's own `postgres` driver):
  1. `pg_get_functiondef('core.notify_lead_assigned')` — live def has the WHERE-predicate form; file now matches it byte-for-byte on that line.
  2. Repro probe: zero-row insert with bare `ON CONFLICT (dedupe_key)` → **ERROR 42P10** ("no unique or exclusion constraint matching the ON CONFLICT specification"); same insert with `WHERE dedupe_key IS NOT NULL` → no error. Confirms both the bug and the fix mechanism.
  3. End-to-end: inside a transaction, inserted a test lead with `assigned_agent_id` set → trigger fired, notification row created for the correct agent (`type=assigned_lead`, correct dedupe_key) → transaction rolled back, no live data changed.
- Flagged for review: **yes** — two things:
  1. **DECISION (stop-list #5, logged not asked):** kept the epoch suffix in `dedupe_key` (`assigned_lead_<lead_id>_<epoch>`). The live e2e test shows the epoch has microsecond precision (`…_1784133672.927601`), so the dedupe index effectively never dedupes assigned-lead notifications — every reassignment produces a new notification. That may be intended (notify on every reassignment) or spam (rapid reassign ping-pong). Minimal/safest option chosen: fix only the conflict clause, change no dedupe semantics. If you want per-(lead,agent) dedupe instead, that's a one-line change to the key construction — product call, review needed.

## [2026-08-02 ~17:30 IST] Baked GI + web export: four silent-failure traps in the Blender API
